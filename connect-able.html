01 · At a glance

The short version

The problem

Staying socially active matters as we age, but a few steps at the entrance, a long walk with no toilet, or the fear of a fall is often enough to keep someone at home. Event listings don't tell you any of that.

The app

Connect-Able matches every event to the City of Melbourne's building accessibility survey, adds a weather forecast and an AI-generated checklist, maps self-guided walks with public toilets, and offers a fall-prevention guide with a personalised questionnaire.

What I did

Connect-Able was my Monash postgraduate capstone (Mar–May 2025), built in an Agile team with industry stakeholders from Coles and Flybuys, where I was a key liaison. In 2026 I brought it back online: fixed the backend, removed leaked keys, self-hosted it behind Cloudflare, rebuilt the event pipeline, and added an analytics page.

02 · Architecture

A static frontend and a phone in a drawer

The frontend is a static Vue build, so Cloudflare Pages serves it free and it stays up even when the backend doesn't. Home, the walks map and the fall-prevention guide need nothing else.

The API and database run on an old Android phone in Termux, alongside my personal site. A Cloudflare Tunnel gives the API a fixed HTTPS address without opening any ports on my home network, and cron jobs restart anything that stops and refresh events each week.

03 · How it works

From an event listing to "can I get in?"

Four parts do the work. Pick one to see the detail.

An event pipeline that runs on a phone

Once a week, a cron job pulls the Eventfinda listings (about 1,400 events at the moment), keeps the Victorian ones in central Melbourne suburbs, splits them into individual sessions, drops sessions already in the past, and writes the rest to MariaDB.

  • Credentials live only in the phone's .env file; a --check run tests them with a single request first.
  • Session times stay in Melbourne local time end to end, so "past" is judged in Melbourne, not UTC.
  • A lock stops a manual run and the cron job from overlapping.

Matching events to rated buildings

Event venues and survey buildings rarely share a name, so each event is scored against nearby buildings: 50% address similarity, 30% distance and 20% name similarity, keeping the best match above 0.7. 

# Only buildings within max_distance can score, so drop the rest with a
# cheap bounding box before the slow geodesic and fuzzy comparisons.
lat_pad = max_distance / 110.574 * 1.2
lon_pad = max_distance / (111.320 * max(np.cos(np.radians(lat)), 0.01)) * 1.2
suburb_buildings = suburb_buildings[
    suburb_buildings['latitude'].between(lat - lat_pad, lat + lat_pad) &
    suburb_buildings['longitude'].between(lon - lon_pad, lon + lon_pad)
]

The original loop compared every event with every building in its suburb, which took over 20 minutes on the phone. The bounding box gives identical matches, 8 times faster.

A weather-aware checklist from Gemini

Each event page fetches the forecast for the session from Open-Meteo, then asks Gemini for 5 to 8 things to bring, given the event, the venue's access notes and the weather: an umbrella in drizzle, a warm layer at 11°C, ID for a licensed venue.

  • The answer is constrained to a JSON array of strings with a response schema.
  • Busy (429/5xx) or slow responses are retried, then sent to a lighter fallback model.
  • If an answer is cut off, only complete items are shown, never a half-written one.
  • The API key travels in a header, so it can't leak into error messages.

An Event Insights page

While waiting for Eventfinda API access I added an analytics page that reads the same live data as the Events page and computes everything in the browser: accessibility mix, age restrictions, start times, weekdays, suburbs and the busiest venues, with a suburb filter and a step-free toggle.

Charts are plain HTML and CSS, with no chart library: one green ramp for access levels, a text label on every bar, and separate dark-mode colours.

06 · Challenges

Problems I solved bringing it back

  1. A backend that never worked in production. Every route used a database connection that was never created. Each request now opens and closes its own connection.
  2. Secrets in git. API keys, a database password and an Eventfinda login were committed. I revoked the leaked keys and moved every credential into environment variables.
  3. Retired AI models and cut-off answers. Google retired the original Gemini models, and the new thinking model ran out of output tokens mid-list. I added retries, a fallback model, a response schema and a parser that keeps only complete items.
  4. A map that went blank. The CARTO base map started requiring an API key. I switched to OpenStreetMap tiles, toned down with CSS to keep the routes readable.
  5. Hosting on a phone. I ported the database from MySQL 8 to MariaDB, found two stale tunnel connectors serving an old config, and fixed a numpy/libc++ mismatch in Termux.
  6. A 20-minute refresh. A bounding-box pre-filter made venue matching 8 times faster with identical results.

07 · Reflection

What I learned

"Live" is a feature

The code was mostly there. What it lacked was everything around it: hosting, secrets, monitoring and fresh data. That's where most of the work went.

Dependencies rot

A map provider, two AI models and a Python package all changed underneath the app within a year. Making the parts configurable kept each fix small.

Look before optimising

The slow refresh looked like a database problem. Reading the matching loop showed the time going on distance maths for buildings that could never match.
